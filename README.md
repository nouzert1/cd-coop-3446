# cd-coop — Crimson Desert co-op, ported to game build 1.0.0.3460

Unofficial two-player co-op mod for **Crimson Desert** (PC / Steam). C++20, loaded as
`cdmp.asi` through Ultimate ASI Loader. Fortnite-style: one player hosts, the other visits their
world.

**Fork of [ByJunter/CrimsonDesertMultiplayer](https://github.com/ByJunter/CrimsonDesertMultiplayer)**,
released by its author under GPL v3 so others could continue. The original targets game build
1.0.0.2976. This fork exists because the game has since auto-updated **2976 → 3424 → 3446 →
3460**, and every hardcoded address in the original is wrong for those builds.

### The one thing that has never been tested

> **Do two PCs connect AND does the guest see the host's character in the world?**

Everything else depends on this. An earlier attempt (mod builds `2BE49E66` × `1B7B429D`) connected
and showed **no character**, and that failure was never explained. A distance readout in the panel
is **not** the same as seeing the character: position exchange can work while the puppet is
invisible. Both must be yes.

This is the highest-value thing a contributor can do. It needs two PCs.

### What the 3460 port did not recover

The game auto-updated from 3446 to 3460 mid-project. Four data globals were re-measured and
**the objects they pointed at have left the region where 3446 kept them** — this is not a
displacement to correct, the whole region was reorganised. See
[docs/research/globais-3460.md](docs/research/globais-3460.md).

| Global | Holds today | Feature lost |
|---|---|---|
| `kCameraSlot` `0x70CDEA8` | `"common.v"` (a string) | guest camera → puppet drawn **without rotation** |
| `kMinimapIconRoot` `0x71B1DD8` | `0xFFFF` | friend's minimap icon |
| `kClientFrameClockMs` `0x70CDCE1` | junk | time sync |
| `kStaticPlayerPos` `0x71C0C20` | two pointers | the self-check (see below) |

**All three consumers fail closed.** `camera_reader` requires an exact sentinel float and reports
`no camera` rather than a wrong camera; `game_clock` has four guards in series and returns
`nullopt`, turning the feature off; the minimap icon is simply not drawn. They do not produce
wrong values.

**Consequence you will see:** the remote character appears unrotated. That is a known limitation,
not a failed test.

## How it works

Crimson Desert is single-player but keeps the client/server architecture of the MMO it grew out
of: the client talks to an in-process "server" through internal messages, internally called
**Troc** (1175 handlers on 3460).

| Path | Role |
|---|---|
| `src/mod/net/troc_sniffer.cpp` | Mid-function hooks on the two functions carrying every client↔server message. Reads them, injects new ones. |
| `src/mod/net/local_capture.cpp` | Your movement and actions, plus game memory (gear, weapon, horse, rope). |
| `src/common/*` | Protocol, reliable fragmented channel, sessions, transports. |
| `src/mod/net/remote_puppet.cpp` | Builds the other player as the server would (`ActorLoadDataAck`) and replays their messages. |
| `src/mod/net/enemy_relay.cpp`, `native_suppress.cpp`, `guest_hits.cpp` | Shared-enemy zone, host-authoritative. |
| `src/mod/game/` | One offsets header per game build, plus readers. |

Connection is **Steam friends only**, via `ISteamNetworkingMessages`. Direct connections are
disabled, so neither player sees the other's IP; traffic relays through Valve.

### Room codes

The host creates a Steam lobby and the mod turns its id into a 7-character Crockford base32 code
(no I, L, O, U). Steam lobby ids are **57-bit** (`0x0186_0000_75C8_6F5D`), not small integers — the
codec encodes the low 32 bits and ORs the constant high bits back on decode. A one-hex-digit slip
in that constant still round-trips internally, so `tests/tests.cpp` pins it against a real captured
lobby id.

The code changes on **every** host restart. For repeated testing, `[steam] peer_steamid` is better:
the guest connects straight to a SteamID64 and needs no code. With neither set, the mod connects to
the only Steam friend currently playing Crimson Desert.

## Building

**Requirements:** Windows 10/11 x64, **Visual Studio 2022** (or Build Tools) with "Desktop
development with C++". Dear ImGui and SafetyHook (with Zydis) are fetched by CMake on first
configure.

```powershell
.\scripts\build.ps1        # configure, build RelWithDebInfo, run unit tests
.\scripts\check-all.ps1    # + offline port verification + two-instance loopback test
```

Install into the game (game closed):

```powershell
.\scripts\instalar-host.ps1              # host profile, 2-PC setup
.\scripts\deploy.ps1 -GameDir "<Steam>\steamapps\common\Crimson Desert\bin64"
.\scripts\deploy.ps1 -Remove
```

Single-PC testing without a second player: `cdmp_peer.exe --mode relay --delay 50`, with
`[net] transport=udp` and `[coop] enabled=1`. Or `.\scripts\testar-um-pc.ps1`.

Two-PC kit:

```powershell
.\scripts\pack-test-kit.ps1 -HostSteamId <SteamID64>
```

> **Both players must use the same ZIP.** The mod compares a build id on connect and shows
> "Different mod versions" as a **warning** — it does not refuse to pair. The packer refuses to
> build a kit from a binary whose build id does not match `HEAD`, because that mismatch shows up at
> the far end as an unexplained warning.

### The build is not bit-reproducible

Measured, not assumed: building identical committed source twice produced binaries differing in
575 KB. MSVC merges `.obj` files in a parallel-dependent order, so the string pool lands at
different offsets and every pointer to it moves. The 33,660 log strings are identical *as a set*.

**This does not affect compatibility**, because the mod compares `kModBuild` — a `constexpr` baked
in from `build_id.h` — not a file hash. Two people building the same commit get different SHA256s
and still pair correctly. The SHA256 in `SHA256SUMS.txt` proves *"this is the file I tested"*; it
does **not** prove *"this came from commit X"*.

## Live verification tooling

The offline verifier reads the shipped `.exe` and never runs the mod, so it cannot catch anything
that only appears at runtime. Bugs in this port were invisible to it and found only in a running
game.

| Tool | What it does |
|---|---|
| `scripts/verify-port.ps1` | Checks every offset against the on-disk executable (RIP-relative arithmetic, section flags, code-vs-data). |
| `tools/probe/` → `cdmp_probe.exe` | External read-only memory reader. `read`, `dump`, `disasm`, `rtti`, `vtables`, `classes`, `scan`, `troc`, `chain watch`. |
| `scripts/comparar-globais.ps1` | Compares data globals between two builds. |
| `scripts/port-3424-probe.ps1`, `docs/PORT-*.txt` | Porting transcripts: which address was measured how. |

### Three traps in `cdmp_probe`, all hit in this port

Each produced a confident, specific, **wrong** number — the most expensive failure mode here.

1. **`troc <begin> <end>` arguments are POSITIONAL.** `--begin X --end Y` is silently ignored and
   the default range is swept. Returned 0, which looked like "the array is not here". It was there,
   shifted by `+0x4000`.
2. **`xrefs` reports the address of the shifted operand, not the instruction start.** Three "sites"
   for one global were one instruction counted three ways.
3. **`scan` without `--heap` does not read live memory.** It returned 0 for a vtable that
   demonstrably existed; `scan --heap` found it immediately.

Two more, about reading output:

4. The module prefix is **`exe+0x…`** when reading the module and `0x…` when reading the heap. A
   regex anchored on `^\s*0x` silently returns nothing.
5. Output may end with `(decimal)` and/or `-> object .?AVName@pa@@`. Take the value after `:`,
   not the first hex match (that is the address).

**Section names in this binary are decoys and are reshuffled every patch.** Select code sections by
`IMAGE_SCN_MEM_EXECUTE` and by content, never by name.

## Engineering rules

These exist because breaking them crashes the game. `CONTRIBUTING.md` has the full set.

- No inline hooks mid-function (`safetyhook::create_mid`) — the instruction may be a jump target.
- Every game memory read is guarded (`VirtualQuery` + SEH).
- Never identify an entity across two PCs by its memory address.
- No work in `DllMain`.
- Bump `kVersion` for any protocol change and serialize field by field.
- The version guard is a **PE timestamp comparison** and refuses to install on an unknown build, on
  purpose, so the mod can never corrupt a save it does not understand.

## Safety and privacy

- The mod only talks to the other player, through Steam networking, and accepts only Steam friends.
  No telemetry, no server of its own.
- Packet recording (`[sniffer] record`) is **off** by default. When on, captures and `cdmp.log`
  contain in-game data (positions, actor keys) — review before sharing.
- **Back up your saves** (`%LOCALAPPDATA%\Pearl Abyss\CD\save`) before testing, and do not save while
  the other player is in your world. That is the most likely way to damage a save.
